# 2026-09-03 — Phase one runs, and what the design got wrong

Implemented the resolver against the five recorded scenarios. Everything is green: ruff, strict
mypy, 23 tests, five scenarios scored against truth sets, pins verified, worked example still
validating.

## The design mostly held

Seventeen decisions written before any code, and the code follows them without argument in almost
every case. `ArtifactRef` enforcing pinned-iff-revision, `Edge` refusing an unresolvable edge with a
strong verdict, `ResolutionReport` refusing partial-without-transient — all of these are three-line
validators that were obvious to write because the decision had already been argued.

The CycloneDX mapping was the strongest case. DEC-013 specified where every field goes, and emitting
a schema-valid BOM was mechanical; the generated document validates against the vendored 1.7 schema
on the first attempt. Deciding the awkward part (that `conformance.score` cannot hold a three-valued
verdict) months before writing the serializer meant there was nothing to rediscover.

## What the first run found

Four disagreements between the tool and the truth sets. **None was a resolver bug.**

**A truth-set defect.** `declared-base` expected four edges and got five. The extra one —
`llama-70b-instruct requires-package transformers` — genuinely exists in the base model's metadata.
I had authored the root's edges plus the second-hop lineage and forgotten that expanding a node
yields *all* its declared edges, not just its ancestry. Classified before editing, per the
evaluation plan, and the expectation corrected with the classification recorded in place.

**An evaluator defect.** `transferred-namespace` scored as inventing an edge it was supposed to
emit. The scenario's `expected-absent.yaml` forbids that edge *conditionally* — `without:
declared_as`, and separately `verdict_if_emitted: verified` — and my scorer matched on
source/target/relation while ignoring the qualifiers. A conditional forbid read as absolute scores a
correct tool as fabricating.

**Two fixture defects.** `transient-failure` and `withdrawn-base` were missing interactions their
scenarios always needed: the first because the root declares a dataset as well as a base, the second
because telling a `held` namespace from a `held-empty` one requires asking whether it still
publishes anything, and I had captured only the organization's existence. Both were gaps in the
capture, not the expectation.

Worth noting that the registry seam refusing to invent a 404 for a missing interaction is what
turned both into loud failures instead of silent wrong answers.

## The one real design gap — DEC-018

`withdrawn-base` failed on `provenance`, and the disagreement turned out to be between two of the
scenario's *own* expected files: `expected-graph.yaml` said `asserted-by-card`,
`expected-unresolvable.yaml` restated the same edge as `unresolvable`. I had written both and not
noticed they contradicted.

DEC-004 settles it — the class exists so a consumer can see "whether a human wrote it down or the
tool established it", which is a question about the *claim*. Microsoft's card plainly asserts that
base; the repository was withdrawn afterwards. Folding the target's fate into the claim's origin
loses the distinction the field exists for, and makes a withdrawn base indistinguishable from a
reference nobody could parse.

So provenance describes how the claim was found; unreachability lives on the node. `unresolvable` is
now reserved for a reference that could not be constructed at all, which is `prose-only-base` and
nothing else so far. The name is broader than the meaning, and renaming it would churn the
CycloneDX mapping for a wording improvement.

That contradiction was invisible for five sessions of design work and surfaced within a minute of
running code against it. It is the clearest argument I have for building something.

## What phase one establishes, and does not

Every edge it emits is `unverifiable`. That reads like a broken tool and is the finding: cards name
a base and stop, so resolution establishes that the named artifact exists and can be pinned, never
that the derivation happened. A test pins it — `test_no_edge_is_ever_verified_in_phase_one` — so
that a future change producing a `verified` edge has to argue for it rather than slip through.

Two guards I was glad to have while implementing. The strict `Edge` validator caught an early
version that emitted an unresolvable edge with evidence attached and no target. And mypy flagged the
deliberately-invalid test code, which is a small piece of evidence that the model is strict enough
for static analysis and the runtime to agree.
